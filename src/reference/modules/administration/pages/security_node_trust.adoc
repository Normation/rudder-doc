= Node-server trust and certificates

This page explains how Rudder uses keys and certificates to secure the data sent by nodes and the communications
between nodes and their policy server, and the options to customize them.

In this page, the _policy server_ refers to the server a node is connected to, either a relay or the root server.

[[overview]]
== Keys and certificates

Rudder uses keys and certificates in three areas. By default, they all rely on the same keys and certificates,
generated by Rudder, and each of them can be customized:

[cols="1,2,2", options="header"]
|===
|Area|Default|Customization
|<<file-signing,Node identity and file signing>>
|Each agent has its own key pair and self-signed certificate, generated at installation
|The node certificate can be registered on the server before the node's first inventory
|<<node-server-communication,Node-server communication>> (TLS)
|<<pinning,Pinning>>: nodes and servers authenticate each other with their agent keys
|<<custom-server-certificate,Pinning with a custom server certificate>>, or
<<ca-certificates,CA-validated certificates>>
|xref:administration:security_web.adoc#web-certificate[Web interface and API] (TLS)
|The certificate used for node-server communication
|A custom certificate for the Web interface and API
|===

[[file-signing]]
== Node identity and file signing

Each agent has:

* a 4096-bit RSA private key (`/var/rudder/cfengine-community/ppkeys/localhost.priv` on Linux)
* a self-signed X.509 certificate for this key (`/opt/rudder/etc/ssl/agent.cert` on Linux), with `UID=<node id>` in its Subject DN

They are generated at agent installation. On Linux, the agent regenerates the certificate if it does not match the key or the node ID.

The agent uses them to sign the inventories, reports and shared files (sent with the `sharedfile_*` methods) it sends to the server.
The server knows the node certificate from the node's first inventory, and trusts it when the node is accepted
(Trust On First Use, _TOFU_). The node certificate can later be managed through the https://docs.rudder.io/api/#tag/Nodes[nodes API].
Once a node is accepted, its inventories and reports are checked against its certificate before being accepted.

These keys and certificates are always used for file signing, regardless of the <<node-server-communication,node-server communication>> configuration.

[[pre-provision-node]]
=== Pre-provision the node on the server

Instead of trusting the certificate sent by the node on first use, you can register it on the server
during your node provisioning process, with the https://docs.rudder.io/api/#tag/Nodes/operation/createNodes[node creation] API.
Provide the `accepted` status, and the `agentKey` parameter with the content of `/opt/rudder/etc/ssl/agent.cert` on the node as `value`.
With the default `certified` key status, the signature of the node's inventories is enforced from the start.

Once the node sends its first inventory, if the node ID and certificate match the pre-provisioned entry, the node inventory is updated.

You can also pre-define node properties using this API, to ensure that the pre-provisioned node immediately joins the correct groups.

[[node-server-communication]]
== Node-server communication

Nodes communicate with their policy server using two protocols, both using TLS 1.3:

* *HTTPS* (`443/tcp`): used by all nodes to send inventories and reports, and to fetch files. Windows nodes also use it
to fetch their policies.
* *Rudder file copy protocol* (`5309/tcp`): a custom file copy protocol inside TLS, used by Linux nodes to fetch
their policies and shared files. It can be disabled with the <<https-only,HTTPS-only mode>>.

These communications can be secured in three ways. The chosen mode is global to a Rudder instance:

[cols="1,2,2,2", options="header"]
|===
|Mode|Server certificate|Node authenticates the server|Server authenticates the node
|<<pinning,Pinning>> (default)
|The server's agent certificate
.2+|Pinned server key hash
.2+|Pinned node key for file downloads, signatures for inventories and reports
|<<custom-server-certificate,Pinning with a custom server certificate>>
|A certificate provided by the user
|<<ca-certificates,CA-validated certificates>>
|A CA-signed certificate provided by the user
|Certificate validation with the CA
|Certificate validation with the CA, and node ID check
|===

[[pinning]]
== Pinning (default)

By default, nodes and policy servers authenticate each other peer-to-peer, using the keys and certificates
used for <<file-signing,file signing>>, without any certificate authority:

* *HTTPS*: the node pins the policy server's public key (with a SHA-256 hash of the key). There is no client authentication,
except for policy and file downloads, which use client certificate authentication (_mTLS_) with the agent certificate.
* *Rudder file copy protocol*: the node and the policy server pin each other's public key (with an MD5 hash of the key).

By default, the node trusts the server key hash received with its first policies (_TOFU_). If the server key changes,
the node refuses to connect, unless the new key hash has been <<new-server-key,distributed beforehand>>.

[[pre-establish-trust]]
=== Pin the server key during provisioning

To establish trust from the start instead of trusting the first connection, provide the server key hash when
configuring the agent.

On the policy server, get the key hashes of its agent key with:

----
# rudder agent info
[...]
Key/Certificate
           Key hash: MD5=595221aa16c00dcec78ba1259d7708de
           Key hash: sha256//2cMrJbjcdh25hJkzFVlyKs62DXsaFmumbcFpQ6/ZguU=
[...]
----

On the agent, provide the hash to trust when configuring the policy server:

----
# rudder agent policy-server -t sha256//2cMrJbjcdh25hJkzFVlyKs62DXsaFmumbcFpQ6/ZguU= mypolicyserver
----

If the policy server uses a HTTPS port other than `443`, add it with the `-p <port>` option.
The command checks that the key presented by the server matches the provided hash before trusting it.

NOTE: If the policy server presents a <<custom-server-certificate,custom certificate>> with a different key,
provide the hash of this certificate's key instead.

You can check that the trust is established by running the following command:

----
# rudder agent info
[...]
        Key pinning: full
[...]
----

Combined with the <<pre-provision-node,pre-provisioning of the node on the server>>, this establishes mutual trust without any trust on first use.

[[custom-server-certificate]]
== Pinning with a custom server certificate

This mode is identical to the <<pinning,pinning mode>>, but the policy server presents a certificate provided by the user
on HTTPS. It allows, to some extent, avoiding the use of self-signed certificates, while still relying on pinning.

NOTE: As long as the virtual hosts are not xref:administration:security_web.adoc#split-virtual-hosts[split], this certificate
is also used for the Web interface and API. To only change the Web interface and API certificate, see
xref:administration:security_web.adoc#web-certificate[Web interface and API certificate] instead.

The new certificate must have `Digital Signature`, `Key Encipherment` and `Data Encipherment` in its X509v3 `Key Usage`.

You can either:

* *Use a separate certificate for HTTPS*, with its own key or with the existing agent key (`/var/rudder/cfengine-community/ppkeys/localhost.priv`).
It is only used by the Web server, and the Rudder file copy protocol keeps using the agent key.
. If the certificate uses a new key, <<new-server-key,distribute the new key hash>> to the nodes first.
. Place the private key in `/opt/rudder/etc/ssl/server.key`.
. Place the certificate in `/opt/rudder/etc/ssl/server.cert`.
. Reload the Web server with `systemctl reload apache2` (or `systemctl reload httpd` depending on your OS).

* *Replace the server's agent certificate* (`/opt/rudder/etc/ssl/agent.cert`) with a certificate issued for the same key
(`/var/rudder/cfengine-community/ppkeys/localhost.priv`), with `UID=<node id>` in its Subject DN (`UID=root` on the root server).
Otherwise, the agent will regenerate a self-signed certificate. As the key does not change, the nodes do not need to be updated.

[[new-server-key]]
=== Distribute a new server key hash

When the server presents a certificate with a new key, the nodes must first learn the new key hash:

. Get the new key hash with:
+
----
echo "sha256//$(openssl pkey -in private.key -pubout -outform der | openssl dgst -sha256 -binary | openssl enc -base64)"
----
. In `/opt/rudder/etc/rudder-web.properties`, set `rudder.server.certificate.additionalKeyHash` to this hash
(several hashes can be separated by a semicolon `;`). The hash of the server's agent key is always trusted, and does not need to be added.
. Restart the webapp with `systemctl restart rudder-jetty`.
. Wait for the new configuration to be applied on all agents before installing the new certificate. Usually, waiting for 24h is enough,
but do not forget nodes that might be down during this period.

Keep this setting as long as the server presents a certificate with this key.

[[https-only]]
== HTTPS-only mode

By default, Linux nodes get their policies from their policy server on `5309/tcp`, and send their reports on `443/tcp` (HTTPS).
Windows nodes always only use HTTPS on `443/tcp`.

You can configure Linux nodes to only use HTTPS on `443/tcp`. This mode can be used with <<pinning,pinning>>,
and is required to <<ca-certificates,use CA-validated certificates>>.

=== Limitations

Limiting Linux nodes to `443/tcp` comes with the following limitations:

* **Remote agent runs from the server's Web interface are not possible**, as they rely on the `rudder-cf-serverd` service running on the node and using `5309/tcp`.
* **Recursive file copies from the server's shared folder to the nodes are not possible.** Only individual file copies with the `file_from_shared_folder` method work.
* Relay synchronization only works in the xref:administration:relayd.adoc#_synchronization_via_ssh[rsync mode], which is not the default and requires additional configuration.

=== Configure the nodes

Configure the nodes first, and only then turn off `5309/tcp` on the server.

On each Linux node, edit the agent configuration file `/opt/rudder/etc/agent.conf` (create it if absent) and add the line:

[source,ini]
----
https_only=true
----

Then check that the agent still works properly with `rudder agent run`.

=== Configure the server

The server doesn't need any additional configuration to serve nodes using HTTPS only.

To also stop using `5309/tcp` on the server, add the following parameter to `/opt/rudder/etc/rudder-web.properties`:

[source,ini]
----
rudder.server.certificate.httpsOnly=true
----

Then restart the webapp with `systemctl restart rudder-jetty`.

This disables the Rudder file copy protocol and the `rudder-cf-serverd` service everywhere (on the server, relays and nodes).
The configuration is propagated to the nodes by the server and is persistent: `rudder-cf-serverd` will be stopped and
disabled on the server and nodes. To revert it, you will have to do it manually on the nodes (or using a Rudder technique).

[[ca-certificates]]
== CA-validated certificates

NOTE: This mode is experimental.

In this mode, all communications use HTTPS (it requires the <<https-only,HTTPS-only mode>>), and are authenticated
with certificates provided by the user and signed by a certificate authority (CA), on both sides:

* These certificates are not related to the keys and certificates generated by Rudder, which are still used for
<<file-signing,file signing>>.
* These certificates are unknown to the Rudder server. Their management (issuance, renewal, etc.) is up to the user.
* They are standard TLS certificates, except that node certificates must contain the node ID, in the Subject DN by default
(like the agent certificate), or <<node-id-in-san,in the Subject Alternative Name>>.
* They are validated everywhere in the standard way, with the system CAs or with a custom CA, global to the Rudder instance.
For policy downloads, the policy server also checks that the node ID in the certificate matches the requested policies.
* Each policy server can use a single certificate for both roles (HTTPS client and server, in `agent-http.cert`),
or separate certificates (`agent-http.cert` for the client, and `server.cert` for the server).

=== Certificate requirements

On each node (including the server and relays), you need for the agent:

* A private key. There is no specific requirement on its type (as long as it can be used with TLS 1.3) or size.
* An X.509 certificate signed by your CA. It must:
** have `digitalSignature` as `keyUsage`
** have a Subject DN containing `UID=<node id>`, where `<node id>` is the node's ID in Rudder. If this is not possible,
the node ID can be put in the `Subject Alternative Name` extension instead (see <<node-id-in-san>>).

On the server and relays, the certificate used by the Web server must have:

* the server's hostname in the `Subject Alternative Name` extension. It can hence be a standard Web server certificate
(compatible with _Let's Encrypt_ for example).
* `digitalSignature` and `keyEncipherment` as `keyUsage`

NOTE: The hostname included in the certificate must be the one used by the agents to connect to the server (their policy server configuration).

If you use the same certificate for the server's agent and the Web server, it must contain both the node ID and the server's hostname.

=== Install the certificates on the nodes

On each node:

* Place the agent private key in:
** `/opt/rudder/etc/ssl/agent-http.key` on Linux
** `C:/Program Files/Rudder/etc/ssl/agent-http.key` on Windows
* Place the agent certificate in:
** `/opt/rudder/etc/ssl/agent-http.cert` on Linux
** `C:/Program Files/Rudder/etc/ssl/agent-http.cert` on Windows
* If you use a custom CA, put the CA certificate (with intermediate certificates if needed) in:
** `/var/rudder/lib/ssl/policy_server_ca.pem` on Linux
** `C:/Program Files/Rudder/lib/ssl/policy_server_ca.pem` on Windows
+
This is required for the first connection only: this file is then managed by the policies, with the CA configured on the server
(`rudder.server.certificate.ca.path`), and is removed if no CA is configured. Without this file, the system CAs are used
(on Windows, the agent then uses the `SChannel` SSL backend).

Edit the agent configuration file `/opt/rudder/etc/agent.conf` on Linux, and add the lines:

[source,ini]
----
https_only=true
cert_validation=true
----

On Windows, the agent always uses HTTPS: only add `cert_validation=true` to `C:/Program Files/Rudder/etc/agent.conf`.

=== Install the certificates on the server and relays

Install the certificate and key of the server's agent:

* Place the private key in `/opt/rudder/etc/ssl/agent-http.key`
* Place the certificate in `/opt/rudder/etc/ssl/agent-http.cert`

If you use a separate certificate and key for the Web server:

* Place the private key in `/opt/rudder/etc/ssl/server.key`
* Place the certificate in `/opt/rudder/etc/ssl/server.cert`

=== Configure the server

Add the following parameters to `/opt/rudder/etc/rudder-web.properties`:

[source,ini]
----
rudder.server.certificate.httpsOnly=true
rudder.server.certificate.validation=true
# If omitted, the system CA store is used
rudder.server.certificate.ca.path=/path/to/ca.pem
----

* `rudder.server.certificate.httpsOnly` enables the <<https-only,HTTPS-only mode>>.
* `rudder.server.certificate.validation` enables certificate validation for all HTTPS connections. It requires `rudder.server.certificate.httpsOnly`.
* `rudder.server.certificate.ca.path` is the CA used to validate certificates. It is distributed to all nodes, relays and the server itself,
in `/var/rudder/lib/ssl/policy_server_ca.pem`. When omitted, the system CA store is used.

Then:

. Restart the webapp with `systemctl restart rudder-jetty`.
. Run the agent on the Rudder server to apply the changes: `rudder agent run`.

The configuration changes are propagated to the nodes by the server, and are persistent on the nodes, to prevent downgrade attacks.
To change one of these parameters later, you need to update it on all nodes.

[[node-id-in-san]]
=== Node ID in the Subject Alternative Name

By default, the server looks for the node ID in the `UID` attribute of the certificate's Subject DN. If you cannot issue such certificates,
you can put the node ID in the Subject Alternative Name (`SAN`) instead, and adapt the Web server configuration.

Create the `/opt/rudder/etc/rudder-apache-nodes-auth.conf` file, which is automatically included by the Web server configuration:

[source,ini]
----
# Not used by the auth process, only for logging purpose
SSLUserName SSL_CLIENT_SAN_DNS_1

# RewriteCond only matching a node of ID equal to $1
RewriteCond "%{SSL:SSL_CLIENT_SAN_DNS_0}=$1.example.com" "^(.+)=\1$" [OR]
RewriteCond "%{SSL:SSL_CLIENT_SAN_DNS_1}=$1.example.com" "^(.+)=\1$"
----

* The optional `SSLUserName` value allows showing the node ID as user name in the logs. When absent, no user is logged (`-` in the log).
* The `RewriteCond` lines must only match a valid certificate for the requested node:
** `$1` is the node ID extracted from the requested URL.
** The first part is a value extracted by Apache from the certificate (see the list of available variables in the Apache documentation).
When using a DNS entry in the SAN, you need to specify the index of the entry. You can use `[OR]` to allow matching the ID from several places in the certificate.
** Replace `example.com` by the domain used in your certificates. For example, if the first DNS entry of the SAN contains `rudder-<node id>.company.com`,
the condition is `RewriteCond "%{SSL:SSL_CLIENT_SAN_DNS_0}=rudder-$1.company.com" "^(.+)=\1$"`.

Then apply the change with `systemctl reload apache2` (or `systemctl restart httpd` depending on your OS).

To get detailed information about the `RewriteCond` matching, add:

[source,ini]
----
LogLevel alert rewrite:trace4
----

It produces detailed logs for each request:

[source,ini]
----
[Wed Oct 29 22:11:18.072897 2025] [rewrite:trace4] [pid 64704:tid 64722]
mod_rewrite.c(4305): [client 192.168.2.3:59478] 192.168.2.3 - -
[server/sid#7f5c26168a08][rid#7f5c242290a0/initial] RewriteCond:
input='18c3a1a6-2dad-40eb-a1dd-2fb04a070d94.test=18c3a1a6-2dad-40eb-a1dd-2fb04a070d94.test'
pattern='^(.*?)=\\1' => matched
----

[[troubleshooting]]
== Troubleshooting

=== Services

In HTTPS-only mode, check that the `rudder-cf-serverd` service is stopped and disabled with `systemctl status rudder-cf-serverd.service`:

[source,ini]
----
rudder-cf-serverd.service - CFEngine file server
	Loaded: loaded (/lib/systemd/system/rudder-cf-serverd.service; disabled; preset: enabled)
	Active: inactive (dead)
----

=== Certificates and keys

To check a node's certificate:

* The command `openssl x509 -in agent1.pem -noout -subject` should return a line like `subject=UID=1ba6a1b9-e7d4-4588-a760-f6405ec3d445`.
If the `UID` is not present (and not configured in the <<node-id-in-san,SAN>>), the node will not be able to download its policies from the server, even if the certificate is valid.
* For server certificates, the command `openssl x509 -noout -ext subjectAltName -in server.cert` should return something like:
+
[source,ini]
----
X509v3 Subject Alternative Name:
	DNS:<policy server hostname>
----

To check the certificate chain from the node, you can use:

[source,ini]
----
openssl s_client -cert_chain /opt/rudder/etc/ssl/agent-http.cert -key
/opt/rudder/etc/ssl/agent-http.key -verifyCAfile
/var/rudder/lib/ssl/policy_server_ca.pem <SERVER HOSTNAME>:443
----

=== Pinned public key mismatch

If agents fail with `curl: (90) SSL: public key does not match pinned public key`, the server key does not match the one pinned by the agent.
Check if the server certificate was <<custom-server-certificate,replaced>>, or if a network security product intercepts the connection
(see xref:administration:troubleshooting.adoc#_curl_90_ssl_public_key_does_not_match_pinned_public_key[troubleshooting]).
