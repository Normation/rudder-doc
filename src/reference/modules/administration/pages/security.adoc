= Security & hardening
:page-aliases: reference:security.adoc

Rudder provides secure defaults whenever possible. This page describes the security model
and lists the actions you can take to harden your installation, with links to the detailed procedures:

* xref:administration:security_network.adoc[Network security]: network flows, firewall rules and ports
* xref:administration:security_node_trust.adoc[Node-server trust and certificates]: how nodes and servers authenticate each other, and how to strengthen it
* xref:administration:security_web.adoc[Web interface and API security]: HTTPS, authentication and user management

[[security-model]]
== Security model

=== Data confidentiality

Rudder is designed to strictly separate policies between nodes, and to only let a node access its own policies.

All confidential information should be stored in node-specific data, namely:

* the directives, groups, rules, and their parameters
* the technique parameters in the technique editor
* the shared-files directory

This data is:

* always transferred encrypted (using the agent copy protocol or HTTPS for nodes, and HTTPS for the Web interface and the API)
* only available to the nodes that need it
* only accessible locally to the users that need it:
** *root server*: all the data is present. Files are only accessible to the `root` user and the Rudder service users.
The backends (PostgreSQL, OpenLDAP) only listen on the loopback interface by default and use Rudder-specific accounts,
whose passwords are only readable by privileged users. Remote access is only possible through the Web interface
(with an authorized user account) or the API (with a token).
** *relay*: only the data needed for the relay itself and the nodes it serves is stored locally, only accessible to the `root` user.
** *node*: only the data needed to configure the node is stored locally, only accessible to the `root` user.

Some content is common to all nodes, and is readable by any node in the
xref:administration:security_network.adoc#allowed-networks[allowed networks], and by all users on the nodes:

* the common ncf part (`/var/rudder/ncf/common`), which includes all the content distributed in the `ncf` package
* the Rudder technique sources, without their parameters (`/var/rudder/configuration-repository/techniques`)

Never store secrets in technique sources. To use secrets in your policies, see
xref:rudder-by-example:ROOT:policies/using-secrets-in-configuration-policies.adoc[using secrets in configuration policies].

=== Node-server communication

* All communications between nodes, relays and the root server are encrypted with TLS 1.3.
* Each agent has its own key pair and certificate, used to sign the inventories, reports and shared files it sends.
The server registers the node certificate when the node is accepted, and checks the signatures against it.
* By default, nodes and their policy server authenticate each other by pinning their keys, with trust established on first use.
The trust can be pre-established during provisioning, and the communications can also rely on certificates issued by your own certificate authority.

See xref:administration:security_node_trust.adoc[Node-server trust and certificates] for details.

=== Services

Rudder services run with dedicated users and with limited access to the filesystem when possible.
See the security section of each service:

* xref:administration:webapp.adoc#webapp-security[Webapp]
* xref:administration:relayd.adoc#relayd-security[Relayd]
* xref:administration:slapd.adoc#slapd-security[Slapd]

[[hardening-checklist]]
== Hardening checklist

=== Network

* Do not expose Rudder on the Internet, and use a VPN for nodes outside your private network. If you must expose it,
apply the xref:administration:security_network.adoc#untrusted-networks-mitigations[mitigations for untrusted networks].
* Restrict access to the Rudder ports to the xref:administration:security_network.adoc#network-flows[required network flows] with a firewall.
* Restrict the xref:administration:security_network.adoc#allowed-networks[allowed networks] to the networks containing your nodes.
* If you don't use remote agent runs, xref:administration:security_network.adoc#disable-agent-listener[disable the agent network service] on your nodes.

=== Node-server communication

* Pre-establish trust between nodes and their policy server during provisioning: xref:administration:security_node_trust.adoc#pre-provision-node[register the node certificate]
on the server, and xref:administration:security_node_trust.adoc#pre-establish-trust[pin the server key] on the node.
* Configure nodes to xref:administration:security_node_trust.adoc#https-only[only use HTTPS] to communicate with their policy server.
* Use xref:administration:security_node_trust.adoc#ca-certificates[certificates signed by your certificate authority] and enable certificate validation.

=== Web interface and API

* xref:administration:security_web.adoc#web-certificate[Use a trusted certificate] for the Web interface and API, and enable xref:administration:security_web.adoc#hsts[HSTS].
* Enable xref:administration:security_web.adoc#authentication[multi-factor authentication] and give minimal privileges to users and API tokens.
* Adjust the xref:administration:security_web.adoc#sessions-and-accounts[session timeout and inactive account policy] to your requirements.

=== Server

* Perform Git changes in the configuration repository as the `rudder-webapp` user, with `rudder server su`, and not as `root`.
* Only allow additional writable directories for the webapp when strictly necessary (see xref:administration:webapp.adoc#webapp-security[webapp security]).
* If you use the rsync synchronization for relays, xref:administration:relayd.adoc#_synchronization_via_ssh[restrict the SSH access] of the relays to the root server.
